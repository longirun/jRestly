### 🛠️ Сессия #189

**Аудит «ADR против кода», срез ADR-0044 (interceptor @Order): восьмая «тихая»
находка серии — утечка скопа сортировки.**

- *Подозрение → факт.* ADR-0044 прямо пишет: «Only sorts within a single
  `@WithInterceptor` value array», «The inter-level ordering guarantee
  (Global → Super → Sub → Method) is **not affected**», «Cross-annotation
  ordering still follows declaration order». Код в `MethodMetadata.parseInterceptors`
  (переехал из `HttpTemplateBuilder` в ADR-0051) делал **два** сортирования:
  пер-декларационное `sortedByOrder` (правильное) И финальную глобальную
  стабильную сортировку всего разрешённого списка по `@Order` — поверх всех
  аннотаций и всех уровней. Историческая справка (git blame): глобальная
  сортировка была ещё в оригинальном #122 и тогда ещё и глобальные
  клиентские интерцепторы резортила; ADR-0051 хотя бы их исключил, но
  декларативная утечка осталась.
- *Последствия (оба детерминированы тестом):* (1) sub/method-интерцептор с
  `@Order(-10)` **опережал** super-интерцептор с `@Order(0)` — инверсия
  пирамиды ADR-0029 «Super → Sub → Method»; (2) второй `@WithInterceptor` с
  отрицательным `@Order` выдвигался перед первым — вопреки «cross-annotation
  declaration order». Тихий: при всех нулевых значениях (обычный случай, без
  `@Order`) стаб-сортировка — no-op, так что расхождение видно только когда
  `@Order` реально используется на разных уровнях/аннотациях.
- *Fix минимальный:* финальная глобальная сортировка удалена
  (`MethodMetadata.parseInterceptors`); каждая декларация уже отсортирована
  `sortedByOrder()` внутри себя. Публичный API не тронут; Javadoc
  `@WithInterceptor` уточнён («within each declaration», а не «within each
  scope level» — та формулировка тоже допускала утечку).
- *TDD red-first:* 2 красных теста в `InterceptorResolutionTest`
  (`orderAnnotationDoesNotCrossScopeLevels` — OrderedSuperApi/OrderedSubApi;
  `orderAnnotationDoesNotReorderAcrossAnnotations` — CrossAnnotationApi) —
  красные ровно по целевым ассертам (позиции 0/1 поменяны), зелёные после.
  Все старые порядковые тесты (ADR-0044 ×3, `pipelineOrderingHierarchy`,
  dedup) не тронуты — пер-декларационная сортировка их полностью покрывает.
- *Документы:* ADR-0044 дополнен `## Amendment #189`.
- *Гейты:* `./gradlew test javadoc` — **1203/1203** (core 1123 +
  engine-okhttp 25 + engine-apache5 25 + codec-jackson-xml 15 + benchmarks 15),
  зелёный под `-Werror`, 0 warnings.
- *Вывод по нити:* класс «тихих» багов серии — это **скопы и границы

### 🛠️ Сессия #190

**Аудит «ADR против кода», срез ADR-0041 (request compression): девятая
находка серии — заявленная валидация `algorithm != null` никогда не
реализовывалась, null-алгоритм — тихий no-op компрессии.**

- *Факт.* ADR-0041 §4 («Controller Validation») обещает две проверки:
  `minSizeBytes >= 0` и `algorithm != null`. Git (оригинал #119, `3a2c22f`):
  вошла только пороговая. Плюс тонкость JLS: `algorithm()` — enum-член с
  дефолтом, и `@Compress(algorithm = null)` **не компилируется** («an enum
  annotation value must be an enum constant») — пункт §4 был аспирационным
  с самого начала. Тем не менее рантайм null до сих пор допускал молча:
  `parseCompression` записывал `EffectiveCompression(true, true, null, 0)`,
  `resolveCompressor(null)` → `null` → компрессия **пропускалась без ошибки
  и без заголовка** — «компрессия, которой нет».
- *Fix:* проверка `algorithm != null` добавлена на обоих уровнях
  (интерфейс + метод) через общий package-private seam
  `ControllerValidator.validateCompress(prefix, compress, problems)` (туда
  же переехала пороговая проверка, сообщения не изменены).
- *TDD red-first:* compile-red (stash фикса → 2 ошибки на отсутствие
  `validateCompress`) → зелёный. Грабли: первый вариант теста
  `@Compress(algorithm = null)` в реальном интерфейсе не прошёл даже javac
  (см. выше) — гейт по правилу #58 поставил на seam с proxy-аннотацией
  (единственный способ выразить null-алгоритм мимо javac) + позитивный
  предохранитель.
- *Чисто по остальному срезу:* SPI/enum/реестр/дефолты ModuleInfo/билдеры/
  приоритет «метод > интерфейс > клиент»/опт-аут `enabled=false`/порог
  `>= minSizeBytes`/гард двойной компрессии (статические + динамические
  заголовки в `createHeaders`) — всё совпадает с ADR; `body` и
  `bodyPublisherSupplier` взаимно исключают друг друга (DTO/byte[]/String —
  supplier null; стриминг — bytes null), сжатый байт-тело гарантированно
  идёт через `body()`; `contentCompressors` в `SimpleModuleInfo` —
  `Map.copyOf` (нет бага класса #182); `handleDecompression` — по ADR §5.3 +
  ADR-0057.
- *Документы:* ADR-0041 → `## Amendment #190`.

### 🛠️ Сессия #191

**Аудит «конкурентный жизненный цикл» (идея #187): `CircuitBreaker` чист,
`RateLimiter` — десятая находка серии, но другого класса: платформозависимый
тайминг бюджета ожидания.**

- *Задача:* проверить `InMemoryCircuitBreaker` и `TokenBucketRateLimiter`
  (ReentrantLock + volatile state, `checkAutoHalfOpenTransition` из
  getState/tryAcquirePermission) — подозрение, заведённое в #187.
- *CircuitBreaker — чисто:* весь мутабельный state под lock'ом или volatile;
  реентерабельная вложенность `metrics()` → `checkAutoHalfOpenTransition()` →
  `transitionToHalfOpenState()` (глубина 3, ReentrantLock) — ок; сбой проба в
  HALF_OPEN реоткрывает сразу (поглощает stale-пробы); конфиг валидирует
  жёстко (window ≥ minCalls, wait > 0, permitted > 0).
- *RateLimiter — баг:* `tryAcquire(Duration)` вёл учёт бюджета инкрементально:
  `remainingWaitNanos -= (waitTime - waited)`, где `waited` — возврат
  `Condition.awaitNanos()`, то есть **платформозависимая оценка** фактического
  сна. Инструментация (временные println под `-Drl.debug`) показала на этой
  JVM: `waited` **отрицательный** (-0.1…-4.8 мс) — оценка parkNanos
  перестреливает запрос. Следствия: (а) здесь, на «негативной» платформе,
  формула случайно работает (бюджет списывается на всё время сна);
  (б) на платформе с `waited ≈ waitTime` (нормальная оценка) бюджет не
  списывается вовсе — потерявший гонку за рефиллом токен ждёт второй полный
  период refill **без учёта в timeout** → блокировка до ~2× заявленного
  (контракт ADR-0043: «ожиданием до `timeout`»); (в) при сильно
  отрицательной оценке — преждевременный таймаут.
- *Fix:* бюджет закреплён за абсолютным дедлайном `System.nanoTime()`
  (однократно на входе), остаток пересчитывается из дедлайна на каждой
  итерации через новый package-private seam `RateLimiters.remainingBudget(
  deadlineNanos, nowNanos)` (clamp ≥ 0); возврат `awaitNanos` больше не
  используется для учёта — сон лишь оптимизация, дедлайн — источник правды.
- *TDD:* compile-red (stash фикса → 5 ошибок на отсутствие seam'а) → зелёный.
  Грабли: поведенческий барьерный тест (2 нити + CyclicBarrier, «один рефилл-
  токен в общем 150 мс окне — ровно один победитель, никто не ждёт дольше
  timeout») на старом коде **зелёный именно из-за негативной оценки
  awaitNanos** — платформа маскирует баг. Вывод: когда платформозависимый
  эффект маскирует дефект, гейт ставится на seam (паттерн #190), а
  поведенческий тест остаётся кроссплатформенным предохранителем.
- *Грабли в тесте:* первый вариант барьера (2 стороны, без main) не синхронизировал
  запуск нитей с моментом потребления burst'а — старт нитей pool'а (до ~70 мс)
  сдвигал окна, и оба захвата влезали в свои timeout'ы. Main стал третьей
  стороной барьера: сначала выпил burst, потом отпустил нити — часы refill и
  окна начали от одного момента.
- *Документы:* ADR-0043 → `## Amendment #191`; class-javadoc
  `RateLimiterTest` обновлён.
- *Гейты:* `./gradlew test javadoc` — **1206/1206** (core 1126 +
  engine-okhttp 25 + engine-apache5 25 + codec-jackson-xml 15 + benchmarks 15),
  зелёный под `-Werror`, 0 warnings; конкурентный тест стабилен 5/5 повторов.

### 🛠️ Сессия #194
- *Срез:* ADR-0036 (метрики) × ADR-0046 (прозрачный 401-рефреш) — продолжаю
  «стыковой» свет из #193, беру мелкого кандидата (a) из заметок #193.
- *Находка (12-я в серии):* ADR-0036 §2 — `attempts()` «total attempts
  executed». 401-рефреш — две фазы передачи, делящие **один** счётчик
  (`int[] attemptsHolder` в `exchange()`, `AtomicInteger attemptsRef` в
  `exchangeAsync()`) — вторая фаза затирает первую. Слушатель видел
  `attempts() == 1` и `isRetried() == false` для вызова, физически ушедшего
  на провод дважды; с `@Retry`: 503 → 401 → 200 отчитывался как 1 вместо 3.
  Оба контура (sync/async) — одинаковый дефект.
- *Fix:* фазы суммируются. Sync: значение первой фазы сохраняется в локальный
  `firstPhaseAttempts` перед вторым `executeWithRetries`, после —
  `attemptsHolder[0] = first + holder[0]`. Async: значение берётся в 401-ветке,
  и `secondPhase.whenComplete((r, e) -> attemptsRef.accumulateAndGet(first,
  Integer::sum))` прибавляет его при завершении второй фазы (успех **или**
  сбой) — навешивается раньше продолжения `thenCompose`, поэтому сумма готова
  до `notifyCallComplete`. `executeWithRetries`/`executeAsyncWithRetries` не
  тронуты (контракт «записать своё число попыток» сохранён). Javadoc
  `CallMetrics.attempts()` уточнён (refresh-фаза входит в сумму).
- *TDD:* 3 красных e2e-теста в `ClientMetricsWireMockTest` (новый интерфейс
  `RefreshMetricsClient`: sync 401→200 — expected 2 was 1 + `isRetried()`
  false; sync 503→401→200 с `@Retry(times=3)` — expected 3 was 1; async
  401→200 — expected 2 was 1) — красные ровно по целевым ассертам, зелёные
  после фикса.
- *Грабли/заметка:* номера `attempt` в `onAttemptComplete`/`onRetry` стартуют
  с 1 в refresh-фазе (per-phase, не per-call) — зафиксировано non-goal'ом

- *Задача:* non-goal Amendment #194: после суммирования фаз в `attempts()`

- *Fix:* `attemptOffset` (число передач первой фазы) прокинут через оба

  `executeAsyncWithRetries`/`attemptAsync`/`scheduleAsyncRetry` (async) —
  слушательские номера = `attempt + offset`. Окно retry-политики, backoff
