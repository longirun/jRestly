### 🛠️ Сессия #189

**Аудит «ADR против кода», срез ADR-0044 (interceptor @Order): восьмая «тихая»
находка серии — утечка скопа сортировки.**

- *Подозрение → факт.* ADR-0044 прямо пишет: «Only sorts within a single
  `@WithInterceptor` value array», «The inter-level ordering guarantee
  (Global → Super → Sub → Method) is **not affected**», «Cross-annotation
  ordering still follows declaration order». Код в `MethodMetadata.parseInterceptors`
  (переехал из `HttpTemplateBuilder` в ADR-0051) делал **два** сортирования:
  пер-декларационное `sortedByOrder` (правильное) И финальную глобальную
  стабильную сортировку всего разрешённого списка по `@Order` — поверх всех
  аннотаций и всех уровней. Историческая справка (git blame): глобальная
  сортировка была ещё в оригинальном #122 и тогда ещё и глобальные
  клиентские интерцепторы резортила; ADR-0051 хотя бы их исключил, но
  декларативная утечка осталась.
- *Последствия (оба детерминированы тестом):* (1) sub/method-интерцептор с
  `@Order(-10)` **опережал** super-интерцептор с `@Order(0)` — инверсия
  пирамиды ADR-0029 «Super → Sub → Method»; (2) второй `@WithInterceptor` с
  отрицательным `@Order` выдвигался перед первым — вопреки «cross-annotation
  declaration order». Тихий: при всех нулевых значениях (обычный случай, без
  `@Order`) стаб-сортировка — no-op, так что расхождение видно только когда
  `@Order` реально используется на разных уровнях/аннотациях.
- *Fix минимальный:* финальная глобальная сортировка удалена
  (`MethodMetadata.parseInterceptors`); каждая декларация уже отсортирована
  `sortedByOrder()` внутри себя. Публичный API не тронут; Javadoc
  `@WithInterceptor` уточнён («within each declaration», а не «within each
  scope level» — та формулировка тоже допускала утечку).
- *TDD red-first:* 2 красных теста в `InterceptorResolutionTest`
  (`orderAnnotationDoesNotCrossScopeLevels` — OrderedSuperApi/OrderedSubApi;
  `orderAnnotationDoesNotReorderAcrossAnnotations` — CrossAnnotationApi) —
  красные ровно по целевым ассертам (позиции 0/1 поменяны), зелёные после.
  Все старые порядковые тесты (ADR-0044 ×3, `pipelineOrderingHierarchy`,
  dedup) не тронуты — пер-декларационная сортировка их полностью покрывает.
- *Документы:* ADR-0044 дополнен `## Amendment #189`.
- *Гейты:* `./gradlew test javadoc` — **1203/1203** (core 1123 +
  engine-okhttp 25 + engine-apache5 25 + codec-jackson-xml 15 + benchmarks 15),

- *Вывод по нити:* класс «тихих» багов серии — это **скопы и границы

### 🛠️ Сессия #190

**Аудит «ADR против кода», срез ADR-0041 (request compression): девятая
находка серии — заявленная валидация `algorithm != null` никогда не
реализовывалась, null-алгоритм — тихий no-op компрессии.**

- *Факт.* ADR-0041 §4 («Controller Validation») обещает две проверки:
  `minSizeBytes >= 0` и `algorithm != null`. Git (оригинал #119, `3a2c22f`):
  вошла только пороговая. Плюс тонкость JLS: `algorithm()` — enum-член с
  дефолтом, и `@Compress(algorithm = null)` **не компилируется** («an enum
  annotation value must be an enum constant») — пункт §4 был аспирационным
  с самого начала. Тем не менее рантайм null до сих пор допускал молча:
  `parseCompression` записывал `EffectiveCompression(true, true, null, 0)`,
  `resolveCompressor(null)` → `null` → компрессия **пропускалась без ошибки
  и без заголовка** — «компрессия, которой нет».
- *Fix:* проверка `algorithm != null` добавлена на обоих уровнях
  (интерфейс + метод) через общий package-private seam
  `ControllerValidator.validateCompress(prefix, compress, problems)` (туда
  же переехала пороговая проверка, сообщения не изменены).
- *TDD red-first:* compile-red (stash фикса → 2 ошибки на отсутствие
  `validateCompress`) → зелёный. Грабли: первый вариант теста
  `@Compress(algorithm = null)` в реальном интерфейсе не прошёл даже javac
  (см. выше) — гейт по правилу #58 поставил на seam с proxy-аннотацией
  (единственный способ выразить null-алгоритм мимо javac) + позитивный
  предохранитель.
- *Чисто по остальному срезу:* SPI/enum/реестр/дефолты ModuleInfo/билдеры/
  приоритет «метод > интерфейс > клиент»/опт-аут `enabled=false`/порог
  `>= minSizeBytes`/гард двойной компрессии (статические + динамические
  заголовки в `createHeaders`) — всё совпадает с ADR; `body` и
  `bodyPublisherSupplier` взаимно исключают друг друга (DTO/byte[]/String —
  supplier null; стриминг — bytes null), сжатый байт-тело гарантированно
  идёт через `body()`; `contentCompressors` в `SimpleModuleInfo` —
  `Map.copyOf` (нет бага класса #182); `handleDecompression` — по ADR §5.3 +
  ADR-0057.
- *Документы:* ADR-0041 → `## Amendment #190`.

### 🛠️ Сессия #191

**Аудит «конкурентный жизненный цикл» (идея #187): `CircuitBreaker` чист,
`RateLimiter` — десятая находка серии, но другого класса: платформозависимый
тайминг бюджета ожидания.**

- *Задача:* проверить `InMemoryCircuitBreaker` и `TokenBucketRateLimiter`
  (ReentrantLock + volatile state, `checkAutoHalfOpenTransition` из
  getState/tryAcquirePermission) — подозрение, заведённое в #187.
- *CircuitBreaker — чисто:* весь мутабельный state под lock'ом или volatile;
  реентерабельная вложенность `metrics()` → `checkAutoHalfOpenTransition()` →
  `transitionToHalfOpenState()` (глубина 3, ReentrantLock) — ок; сбой проба в
  HALF_OPEN реоткрывает сразу (поглощает stale-пробы); конфиг валидирует
  жёстко (window ≥ minCalls, wait > 0, permitted > 0).
- *RateLimiter — баг:* `tryAcquire(Duration)` вёл учёт бюджета инкрементально:
  `remainingWaitNanos -= (waitTime - waited)`, где `waited` — возврат
  `Condition.awaitNanos()`, то есть **платформозависимая оценка** фактического
  сна. Инструментация (временные println под `-Drl.debug`) показала на этой
  JVM: `waited` **отрицательный** (-0.1…-4.8 мс) — оценка parkNanos
  перестреливает запрос. Следствия: (а) здесь, на «негативной» платформе,
  формула случайно работает (бюджет списывается на всё время сна);
  (б) на платформе с `waited ≈ waitTime` (нормальная оценка) бюджет не
  списывается вовсе — потерявший гонку за рефиллом токен ждёт второй полный
  период refill **без учёта в timeout** → блокировка до ~2× заявленного
  (контракт ADR-0043: «ожиданием до `timeout`»); (в) при сильно
  отрицательной оценке — преждевременный таймаут.
- *Fix:* бюджет закреплён за абсолютным дедлайном `System.nanoTime()`
  (однократно на входе), остаток пересчитывается из дедлайна на каждой
  итерации через новый package-private seam `RateLimiters.remainingBudget(
  deadlineNanos, nowNanos)` (clamp ≥ 0); возврат `awaitNanos` больше не
  используется для учёта — сон лишь оптимизация, дедлайн — источник правды.
- *TDD:* compile-red (stash фикса → 5 ошибок на отсутствие seam'а) → зелёный.
  Грабли: поведенческий барьерный тест (2 нити + CyclicBarrier, «один рефилл-
  токен в общем 150 мс окне — ровно один победитель, никто не ждёт дольше
  timeout») на старом коде **зелёный именно из-за негативной оценки
  awaitNanos** — платформа маскирует баг. Вывод: когда платформозависимый
  эффект маскирует дефект, гейт ставится на seam (паттерн #190), а
  поведенческий тест остаётся кроссплатформенным предохранителем.
- *Грабли в тесте:* первый вариант барьера (2 стороны, без main) не синхронизировал
  запуск нитей с моментом потребления burst'а — старт нитей pool'а (до ~70 мс)
  сдвигал окна, и оба захвата влезали в свои timeout'ы. Main стал третьей
  стороной барьера: сначала выпил burst, потом отпустил нити — часы refill и
  окна начали от одного момента.
- *Документы:* ADR-0043 → `## Amendment #191`; class-javadoc
  `RateLimiterTest` обновлён.
- *Гейты:* `./gradlew test javadoc` — **1206/1206** (core 1126 +
  engine-okhttp 25 + engine-apache5 25 + codec-jackson-xml 15 + benchmarks 15),
  зелёный под `-Werror`, 0 warnings; конкурентный тест стабилен 5/5 повторов.

### 🛠️ Сессия #194
- *Срез:* ADR-0036 (метрики) × ADR-0046 (прозрачный 401-рефреш) — продолжаю
  «стыковой» свет из #193, беру мелкого кандидата (a) из заметок #193.
- *Находка (12-я в серии):* ADR-0036 §2 — `attempts()` «total attempts
  executed». 401-рефреш — две фазы передачи, делящие **один** счётчик
  (`int[] attemptsHolder` в `exchange()`, `AtomicInteger attemptsRef` в
  `exchangeAsync()`) — вторая фаза затирает первую. Слушатель видел
  `attempts() == 1` и `isRetried() == false` для вызова, физически ушедшего
  на провод дважды; с `@Retry`: 503 → 401 → 200 отчитывался как 1 вместо 3.
  Оба контура (sync/async) — одинаковый дефект.
- *Fix:* фазы суммируются. Sync: значение первой фазы сохраняется в локальный
  `firstPhaseAttempts` перед вторым `executeWithRetries`, после —
  `attemptsHolder[0] = first + holder[0]`. Async: значение берётся в 401-ветке,
  и `secondPhase.whenComplete((r, e) -> attemptsRef.accumulateAndGet(first,
  Integer::sum))` прибавляет его при завершении второй фазы (успех **или**
  сбой) — навешивается раньше продолжения `thenCompose`, поэтому сумма готова
  до `notifyCallComplete`. `executeWithRetries`/`executeAsyncWithRetries` не
  тронуты (контракт «записать своё число попыток» сохранён). Javadoc
  `CallMetrics.attempts()` уточнён (refresh-фаза входит в сумму).
- *TDD:* 3 красных e2e-теста в `ClientMetricsWireMockTest` (новый интерфейс

  401→200 — expected 2 was 1) — красные ровно по целевым ассертам, зелёные
  после фикса.

  с 1 в refresh-фазе (per-phase, не per-call) — зафиксировано non-goal'ом

  там некапнутый `Retry-After` в `RetryPolicy`, здесь — в декорализованном
  джиттере реконнекта.

### 🛠️ Сессия #207

**Free-аудит (нитка «дублирующие входные пути» → контракт `ControllerValidator`):
невалидный `@Retry` проскакивал eager-валидацию — 17-я «тихая» находка серии,
класс #190 «заявленная защита есть не у всех зеркальных путей».**

- *Ход:* свободный выбор из контекста #206 (активная зона пуста, highest ADR
  0060). Вместо длинного среза взял точечную сверку «одинаковая функция —
  разные входные пути» (#200) на уровне декларативных аннотаций: какие из них
  валидируются eager'ом в `ControllerValidator`, а какие нет.
- *Факт.* Инварианты `@Retry` (`times >= 1`, `multiplier >= 1.0`,
  `initialBackoffMs <= maxBackoffMs`, `statuses ∈ [100,599]`) объявлены в
  ADR-0040 и реализованы в `RetryPolicy.Builder.build()`. Но `build()` вызывается
  **лениво** в `MethodMetadata.parse` — на **первом вызове** метода. При этом
  `ControllerValidator` eager-валидирует инварианты каждой другой декларативной
  аннотации: `@Timeout`, `@Compress`, `@Trace`, `@CircuitBreaker`,
  `@RateLimiter`, `@Accept`, `@ContentType`, `@Cookie`, `@OnError`,
  `@QueryCollectionFormat`, `@RequestParam` — с агрегированным actionable-
  сообщением при создании прокси. `@Retry` был **единственной дырой**.
- *Последствие.* Контроллер с `@Retry(times = 0)` (или `multiplier = 0.5`,
  или инвертированным backoff, или `statuses = {999}`) проходил
  `validateControllers(true)` (дефолт), прокси создавался, и первый вызов падал
  голым `IllegalStateException` из недр `MethodMetadata.parse` — без имени
  метода/поля, в отличие от стандартного `ControllerValidationException`. Тихая:
  при корректной конфигурации всё хорошо, расхождение видно только на
  некорректном входе.
- *Fix.* Новый `ControllerValidator.validateRetry` зеркалит правила
  `RetryPolicy.Builder.build()` (все нарушения — в один список, префикс
  `method():`), вызван из `validateMethod`. `maxRetryAfterMs` намеренно не
  проверяется: аннотация сохраняет конвенцию `-1`/отрицательное = «unset»
  (`parseRetryPolicy` пропускает значение при `< 0`). Поведение валидной
  политики не изменилось — те же правила, но на стадию раньше.
- *TDD red-first:* новый
  `ControllerValidationTest.rejectsInvalidRetryConfigurationEagerly` — 4 целевых
  проблемы + eager `ControllerValidationException` при `client.get(...)` +
  no-false-positive на валидной политике. Красный на до-фикс коде ровно по
  `assertEquals(4, problems.size())` (список пуст) → зелёный.
- *Документы:* ADR-0040 → `## Amendment #207`.
- *Гейты:* `./gradlew test javadoc` — **1233/1233** (core 1153 +
  engine-okhttp 25 + engine-apache5 25 + codec-jackson-xml 15 + benchmarks 15),
  0 failures/errors, javadoc зелёный под `-Werror`, 0 warnings.
- *Non-goals (наблюдение, не трогал):* `@ExpectStatus` и `@FollowRedirects`
  тоже не валидируются, но их инварианты нигде не объявлены — это не «дыра»,
  а новая фича (отдельное решение). `@HttpVersion` — enum, ограничений нет.
- *Вывод по нити:* у перегрузок одного сеттера защита есть не у всех (#200);
  тот же приём, поднятый на уровень аннотаций: у одной «семьи» декларативных
  аннотаций eager-валидация есть у всех, кроме одной. Сверять состав семьи —
  дешёвый источник находок.

### 🛠️ Сессия #209

**Free-аудит (нитка «семья name-bearing required-атрибутов» → последний член
`@MultipartFormFile.partName`): `partName = ""` тихо уезжал на провод как
`name=""` — 19-я «тихая» находка серии, семья закрыта.**

- *Ход:* свободный выбор из контекста #208 (активная зона пуста, highest ADR
  0060). Довёл до конца приём #207/#208: у семейства name-bearing аннотаций
  (`@Trace.header`, `@Cookie.name`, `@RequestHeader.name`, `@PathVariable.name`,
  `@RequestParam.name`, `@CircuitBreaker.name`, `@RateLimiter.name`,
  `@SetAuthDetails.headerName`) остался **один** невалидируемый член —
  `@MultipartFormFile.partName`.
- *Факт (и пересмотр решения #208).* `@MultipartFormFile.partName` — required
  (без дефолта) и **единственный без fallback на имя Java-параметра**:
  `@RequestParam`/`@RequestHeader`/`@Cookie` в `MethodMetadata.parse` делают
  `name().isEmpty() ? p.getName() : name`, а `partName()` берётся verbatim
  (`multiName = mff.partName()`). Blank ничего не роняет: часть уходит с
  `Content-Disposition: form-data; name=""` — клиент молчит, сервер не может

### 🛠️ Сессия #211

**Free-аудит (ось #210 «парные декларативные конструкции» → форма самой
половины): `path()` глагола не проверялся на URI-легальность — 21-я «тихая»
находка серии.**

- *Ход:* свободный выбор из контекста #210 (активная зона пуста, highest ADR
  0060). #210 закрыл *пару* шаблон ⇄ `@PathVariable`, но не тронул форму самой
  половины — и это был буквально названный в #210 хвост-кандидат
  («`path()` — blank/CRLF/пробелы падает поздно в `URI.create`»).
- *Факт:* `@Get/@Post/@Put/@Patch/@Delete` `path()` (или абсолютный URL) с
  URI-нелегальным символом доживает до **отправки**, где `HttpTemplate.createUri`
  → `URI.create(url)` падает голым `IllegalArgumentException` — без имени
  метода, с индексом в *относительном* пути, а не в собранном URL. Реалистичные
  ловушки (все проверены зондом): пробел → `Illegal character in path at index
  N`; CR/LF → то же (плюс риск инъекции в request-line); **Retrofit/JAX-RS
  `{id}`** вместо `${id}` → падает на `{`; битый percent-escape `/api/100%` →
  `Malformed escape pair`. Тот же класс, что #207–#210.
- *Fix:* `ControllerValidator.validatePath` маскирует `${...}`-плейсхолдеры
  same-length-строкой легального символа (`PATH_PLACEHOLDER.matcher(path)
  .replaceAll(m -> "x".repeat(m.group().length()))` — валидный шаблон не
  спотыкается и индексы выровнены с исходным путём) и прогоняет результат через
  `URI.create`; любое `IllegalArgumentException` уходит в общий агрегированный
  `ControllerValidationException` при создании прокси:
  `method(): path must be a valid URI reference: <reason>`.
- *Почему именно `URI.create`, а не сканер символов:* проверка **точно
  зеркалит** строку, которую реально скормит фреймворк, поэтому ложных
  срабатываний нет. Зонд показал ловушки наивного сканера: Java `URI` **принимает
  non-ASCII** (`/путь`) в path, а `[`/`]` легальны в authority (IPv6
  `http://[::1]/api/items`), но *нелегальны* в path. Ручной whitelist дал бы
  false positive на IPv6-URL и пропустил бы non-ASCII; `URI.create` на
  masked-строке — ноль и того, и другого. Fragment (`#frag`) `URI.create`
  принимает, а JDK-транспорт молча срезает на проводе (проверено raw-TCP
  зондом: request-line `GET /api/x HTTP/1.1`) — оставлен как есть.
- *TDD red-first:* новый
  `ControllerValidationTest.rejectsInvalidUriCharactersInPathEagerly` (пробел,
  `{id}`, битый `%` → 3 проблемы `path must be a valid URI reference` + eager
  исключение; `%20`/`?x=1` и IPv6-URL — no-false-positive) — красный на
  до-фикс коде ровно по `assertEquals(3, problems.size())` → зелёный.
- *Риск ложных срабатываний проверен:* просканировал все `path = "..."` в дереве
  — единственный нелегальный литерал `/users/{id}` живёт в `MethodMetadataTest`
  (unit-тест `MethodMetadata` напрямую, `ControllerValidator` не зовётся) →
  полный прогон зелёный.
- *Документы:* ADR-0025 → `## Amendment #211`.
- *Гейты:* `./gradlew test javadoc` — **1237/1237** (core 1157 +
  engine-okhttp 25 + engine-apache5 25 + codec-jackson-xml 15 + benchmarks 15),
  0 failures/errors, javadoc зелёный под `-Werror`, 0 warnings.
- *Non-goals (наблюдение, не трогал):* `@ExpectStatus(statuses = {})` /

### 🛠️ Сессия #213

**Free-аудит/проектное решение: `0`-таймаут «принимаем, но невыразим» на
JDK-движке — 23-я находка серии, закрытие non-goal #200.**

- *Ход:* свободный выбор из контекста #212 (активная зона пуста, highest ADR
  0060). Взял оставшийся хвост #200: `connectTimeout(0)`/`socketTimeout(0)`
  валидны по ADR-0027 §3 («non-negative»), но JDK `HttpClient.Builder`
  отвергает `Duration.ZERO` — `connectTimeout` **на создании клиента**,
  `HttpRequest.Builder.timeout` **на первом запросе** — голым
  `IllegalArgumentException: Invalid duration: PT0S`. OkHttp/Apache5 при этом

- *Решение (автономия Антона):* **`0` = «без таймаута» на всех движках** —
  backward-compatible чтение (OkHttp/Apache и так так читали), а не отказ от
  нуля (сломал бы существующих).
- *Fix:* единый `HttpTemplate.effectiveSocketTimeout(methodTimeout,
  moduleInfo)` — `@Timeout` всегда побеждает, иначе `socketTimeout == 0` →

  `JdkHttpEngine.create` применяет `connectTimeout` только при `> 0` (дефолт
  JDK — безграничный). Негатив по-прежнему отбивают билдеры (#200), `@Timeout`
  — строго положительный. Javadoc `ModuleInfo`, `SimpleModuleInfo.Builder`,
  `JRestlyClient.Builder`, `HttpEngineOptions` уточнены.
- *TDD red-first:* 2 e2e-теста в `TimeoutWireMockTest` —
  `zeroConnectTimeoutDisablesConnectTimeout` (создание клиента + вызов) и
  `zeroSocketTimeoutDisablesRequestTimeout` (ответ с задержкой) — красные на
  до-фикс коде ровно по `Invalid duration: PT0S` (оба), зелёные после.
- *Документы:* ADR-0027 → `## Amendment #213`.
- *Гейты:* `./gradlew test javadoc` — **1241/1241** (core 1161 +
  engine-okhttp 25 + engine-apache5 25 + codec-jackson-xml 15 + benchmarks 15),
  0 failures/errors, javadoc зелёный под `-Werror`, 0 warnings.
- *Вывод:* «принимаемое значение без определённой семантики» — отдельный
  подкласс находок: валидация уже не пропускает мусор, но легальный вход

  опасен, как его отсутствие. Дёшево и воспроизводимо: у каждой уже
  существующей парной валидации спросить «а обратное направление?».

### 🛠️ Сессия #215

**Free-аудит (продолжение оси #214 «асимметричный guard»): `@RequestBody` на
form-urlencoded/multipart-методе тихо выбрасывался — 25-я «тихая» находка
серии, симметричное закрытие пары «payload-аннотация ⇄ requestType».**

- *Ход:* свободный выбор из контекста #214. Взял подсказку #214 буквально:
  у пары «payload-биндинг ⇄ requestType» была закрыта лишь **одна** половина —
  `@MultipartFormFile` требует `MULTIPART_FORM_DATA` (#214). Вторую
  (`@RequestBody`) никто не проверял.
- *Факт (тихий drop):* `@RequestBody` сериализуется JSON-кодеком и читается
  **только** в ветке `APPLICATION_JSON` (`HttpTemplateBuilder.build` →
  `createJsonBodyPayload`, строка ~292). На `APPLICATION_FORM_URLENCODED` тело
  собирает `createUrlEncodedBody` (только `@RequestParam`), на
  `MULTIPART_FORM_DATA` — `createMultipartParts` (только
  `@RequestParam`/`@MultipartFormFile`); ни один путь не зовёт `createBody` →
  аргумент `@RequestBody` **молча выбрасывается** из запроса (ни ошибки, ни
  лога). Проверено зондом: валидатор молчал (0 проблем). Тот же класс, что
  #207–#214.
- *Fix:* `ControllerValidator.validateMethod` — для каждого
  `@RequestBody`-параметра при `requestType != APPLICATION_JSON` добавляет
  `method(): @RequestBody parameter requires requestType = APPLICATION_JSON` в
  общий агрегированный `ControllerValidationException` при создании прокси.
  `@Get` не затронут (отбивается отдельным сообщением, `resolveRequestType(@Get)`
  = JSON); JSON-путь ведёт себя как раньше. Публичный API не тронут; javadoc
  `ControllerValidator` уточнён (payload-биндинг должен совпадать с requestType).
- *TDD red-first:*
  `ControllerValidationTest.rejectsRequestBodyWithoutJsonRequestTypeEagerly`
  (form-urlencoded + multipart → по 1 проблеме и eager исключение; JSON-метод —
  no-false-positive) — красный на до-фикс коде ровно по
  `assertEquals(1, formProblems.size())` (список пуст) → зелёный.
- *Риск ложных срабатываний проверен:* ни один реальный `@RequestBody` в дереве
  не объявлен на form/multipart-методе — полный прогон зелёный.
- *Документы:* ADR-0035 → `## Amendment #215`.
- *Наблюдение (не трогал):* составной guard остаётся hub-центричным — пара из
  двух `{@PathVariable, @RequestParam, @RequestHeader, @MultipartFormFile}`
  по-прежнему принимается (оба биндинга срабатывают: это double-binding, а не
  тихий drop; хабы `@RequestBody`/`@Cookie` не тронуты).
- *Гейты:* `./gradlew test javadoc` — **1243/1243** (core 1163 +
  engine-okhttp 25 + engine-apache5 25 + codec-jackson-xml 15 + benchmarks 15),
  0 failures/errors, javadoc зелёный под `-Werror`, 0 warnings.
- *Вывод по нити:* семья «payload-аннотация ⇄ requestType» закрыта
  симметрично (`@RequestBody` → JSON, `@MultipartFormFile` → MULTIPART). Приём
  #214 («сверять обе стороны пары») сработал и на второй итерации — стоит
  пройтись так по каждой паре из активной зоны.
