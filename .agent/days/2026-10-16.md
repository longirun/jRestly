### 🛠️ Сессия #148

**Что сделано:** ADR-0058 (Status: Proposed) —
`docs/0.10.0/ADR-0058-external-http-engine-submodules-okhttp-apache5.md`.

Ключевые архитектурные решения, оформленные в документе:

1. **Два субмодуля** `jrestly-engine-okhttp` / `jrestly-engine-apache5`,
   `api`-зависимость на свой транспорт (публичные конструкторы принимают
   `OkHttpClient`/`CloseableHttpClient`). Ядро — 0 зависимостей.
   `benchmarks` — на `project(':engine-*')`, прототипы из
   `ru.jrestly.benchmark.engine` удаляются (один источник правды).
2. **Автообнаружение**: ServiceLoader-регистрация `HttpEngineProvider`
   в каждом субмодуле, `isAvailable()` через `Class.forName`.
   `JdkHttpEngine` провайдером **не является** (остаётся fallback'ом) —
   поведение ядра у пользователя без субмодулей не меняется.
3. **Приоритеты**: `default int priority()` в `HttpEngineProvider`
   (бинарно-совместимое расширение), резолвер — стабильная сортировка по
   приоритету, официальным адаптерам 50 (равенство → порядок ServiceLoader,
   документировать явный выбор при обоих на classpath).
4. **Контракт паритета** — чек-лист по полям `HttpEngineOptions`:
   timeout (callTimeout / RequestConfig), streamResponse (byteStream /
   entity content), version (best-effort), прогресс-листнеры с финальным
   событием и нулевой загрузкой, trailers, `close()` с уважением
   `ownsClient`. Исключительный контракт без изменений.
5. **Маппинг ModuleInfo** в `createEngine`: SSL (ADR-0020) → TLS-транспорт,
   CookieHandler → CookieJar/CookieStore (ADR-0032/0039), ProxySelector →
   per-request прокси (ADR-0037), Authenticator → challenge-интерцептор
   best-effort, virtual threads → virtual-thread executor для колбэков.
6. **Адаптер body publisher**: выкачивание JDK `Flow.Publisher<ByteBuffer>`
   → `InputStream` одним адаптером на стриминг (ADR-0035) и multipart
   (ADR-0024) — единственный «чужой» тип в wire-модели, остальное
   платформо-независимое.

Найдено при исследовании (записано в грабли ADR): `sendAsync` OkHttpEngine
закрывает `Response` в колбэке (стриминг в async не читается),
Apache5 `sendAsync` — supplyAsync на общем ForkJoinPool (истощение потоков),
оба прототипа игнорируют timeout/version/stream/progress и не
регистрируются в ServiceLoader.

**Грабли/находки:**
- Приоритет ServiceLoader-провайдеров — явная недетерминизация
  «первый доступный» в `HttpEngineResolver`; решается `priority()` +
  стабильная сортировка.
- `HttpRequest.BodyPublisher` — из `java.base`, а не из чужой зависимости,
  поэтому генерализация wire-типа не обязательна (Non-Goal, отдельный ADR
  при необходимости).

**Гейты:** ядро не менялось — `./gradlew test` зелёный (UP-TO-DATE, 1058/1058),
0 warnings. Изменены: ADR-0058, DRAFT.md, дневник, mailbox, last_session.

### 🛠️ Сессия #149

  ведут себя как раньше — приоритет 0).

  Зелёные предохранители: стабильность при равенстве, пропуск недоступного
  высокоприоритетного, fallthrough на нижний приоритет при null-движке.
  Хелпер `TestProvider` без `@Override` на `priority()` — компилируется и до
  появления default-метода (чистый assertion-red, не compile-red).

### 🛠️ Сессия #155

**Разгадка «проклятия» сессий #150–#154 + фикс дедлока `PublisherInputStream` (фаза 2a ADR-0058 добита до коммита).**

- В дереве нашлись незакоммиченные следы сессий #150–#154: субмодуль `engine-okhttp`
  (движок + провайдер 50 + ServiceLoader-регистрация + build.gradle с maven-publish
  и javadoc-гейтом + 19 тестов), миграция `benchmarks` на `project(':engine-okhttp')`
  (прототип OkHttp-движка удалён), `settings.gradle`, пометка в ADR-0058. Память
  (дневник/mailbox/last_session) эти сессии не обновляли — коммита не было.
- Причина найдена в старых `test-results`: полный прогон **зависал** на
  `OkHttpEngineParityTest.streamingBodyPublisherIsDrained` (в прошлом прогоне тест
  провисел 488 с и JVM убило лимитом сессии) — так эти сессии и умирали до коммита.
- Диагноз (по jstack зависшего воркера): в `OkHttpEngine.PublisherInputStream`
  маркер `END_OF_STREAM` одноразовый — `read(8192)` добирает остаток последнего
  чанка, попутно съедает END из очереди и возвращает данные; следующий `read`
  поллит уже пустую очередь **вечно**. Второй латентный баг там же: ошибка
  публикатора (`FailureHolder` в очереди) обрабатывалась `continue` без повторной
  проверки `failure` — тоже вечное ожидание.
- Фикс: липкий `volatile boolean eof` (END / ошибка / закрытие → EOF навсегда;
  ошибка — немедленный `throw`), вспомогательный `toIOException`. Стенд-грабли:
  по-чанково репродьюсер НЕ воспроизводит — нужен именно буферный цикл добивки
  (okio `writeAll`), иначе EOF-проба не съедает маркер заранее.
- Гейты: **хэнг устранён** — `:engine-okhttp:test` теперь завершается за 11 с
  (раньше вечно); **17/21 зелёных, 4 падения** — честный WIP, зафиксировано
  ниже. Ядро не менялось (1048 зелёных на #149).

**4 оставшихся падения паритета (разобрать следующей сессией):**
- `Zero-length download fires exactly one (0, 0) event`: событий 0 вместо 1.
- `Download progress ... Content-Length bodies` и `Streaming download progress ...`:
  `total == -1` вместо Content-Length (100000/30000).
- `Multipart bodies are rendered per RFC 7578`: в теле на сервере нет ожидаемой
  строки text-части (остальные ассерты multipart-теста прошли!).
**Ведущая гипотеза одного корня для трёх прогресс-тестов:** OkHttp включает
прозрачный gzip (`Accept-Encoding: gzip` по умолчанию) и после распаковки
`body.contentLength()` = -1; в ядре же декомпрессия — своя (ADR-0021), т.е. это
ещё и риск двойной распаковки — фикс, вероятно, «выключить прозрачный gzip в
движке, привести к контракту ядра». Multipart (передан через тот же
`MultipartBodyPublisher`, что и core-тесты) — вероятно, та же распаковка/кодировка
при чтении тела на WireMock-стороне; проверять вторым шагом.

**Стенд-грабли (в копилку):** зависший тест прятал 4 падения — вечный poll-цикл
маскировал прогресс; всегда запускать модульные тесты с внешним `timeout`.

### 🛠️ Сессия #156

**ADR-0058, фаза 2a закрыта: `:engine-okhttp` полностью зелёный (23/23).**

- Разобраны 4 падения из WIP #155 — методом зонда (временный `ProbeTest`,
  печать сырых заголовков запроса/ответа и multipart-тела через WireMock).
  Факты оказались важнее гипотез: корней два, не один.
- **Прогресс-тесты (`total == -1`, 0 событий):** OkHttp `BridgeInterceptor`
  при отсутствии `Accept-Encoding` инжектит `Accept-Encoding: gzip` и
  **прозрачно распаковывает** ответ — снимает `Content-Encoding`, теряет
  `Content-Length` (`contentLength() == -1`), тело отдаёт распакованным.
  Это ломало и `total` (ADR-0033), и `isDecompressionEnabled()==false`
  (ADR-0021), и метаданные `Content-Encoding` для ядра.
- **Второй корень прогресс-падений (стенд!):** WireMock 3.12 (Jetty) без
  явного `Content-Length` в стабе ВСЕГДА отвечает `Transfer-Encoding: chunked`
  (проверено curl'ом через wiremock-standalone). Core-тесты прогресса поэтому
  декларируют CL явно — parity-тесты #150–154 этого не делали. Фикс стабов
  зеркалит core (`withHeader("Content-Length", ...)`, для пустого — "0").
- **Multipart-падение — баг теста, не движка:** канонический рендер text-части
  (сверено с core-эталоном `MultipartTest.expectedLegacyBody`) содержит строку
  `Content-Type: text/plain; charset=UTF-8` между `Content-Disposition` и
  пустой строкой. Ассерт ждал её отсутствия.
- **Фикс движка — пассивный транспорт (два интерцептора):**
  `NoTransparentGzipInterceptor` (application: при отсутствии `Accept-Encoding`
  подставляет `gzip` + tag-маркер, чтобы Bridge не включил прозрачность) и
  `StripSuppressedAcceptEncodingInterceptor` (network: снимает подставленный
  заголовок ровно перед проводом). Итог: на проводе заголовка нет — точный
  паритет с `JdkHttpEngine`; явный `Accept-Encoding` вызывающего проходит как
  есть, ответ приходит сжатым с живым `Content-Encoding`. Оборачивается и
  внешний `OkHttpClient` (движок = контракт, не сырой OkHttp).
- **TDD:** red-first подтверждён — `noAcceptEncodingInjectedByTransport`
  красный до фикса (`containsHeader("Accept-Encoding") == true`), зелёный после;
  `explicitAcceptEncodingIsPassedThroughCompressed` — регрессионный
  предохранитель (зелёный до и после).
- ADR-0058 дополнен секцией Amendment (решение + побочная находка WireMock).
- **Бонус-находка:** javadoc-гейт субмодуля (`-Xdoclint:all -Werror`, как у ядра)
  в WIP #150–154 **никогда не был зелёным**: `{@link JdkHttpEngine}` не
  резолвился (класс ядра не заимпортирован — javadoc не видит simple name без
  импорта) + implicit default concrete constructor у `OkHttpEngineProvider`
  (doclint missing: «use of default constructor, which does not provide a
  comment»). Фикс: импорт `JdkHttpEngine` и явный конструктор с javadoc.
  `:engine-okhttp:javadoc` теперь зелёный.
- **Гейты: 1086/1086** (core 1048 + engine-okhttp 23 + benchmarks 15),
  0 failures; полный `./gradlew test` — 18 с (хэнг #155 не вернулся);
  `:engine-okhttp:javadoc` — зелёный.
