### 🛠️ Сессия #148

**Что сделано:** ADR-0058 (Status: Proposed) —
`docs/0.10.0/ADR-0058-external-http-engine-submodules-okhttp-apache5.md`.

Ключевые архитектурные решения, оформленные в документе:

1. **Два субмодуля** `jrestly-engine-okhttp` / `jrestly-engine-apache5`,
   `api`-зависимость на свой транспорт (публичные конструкторы принимают
   `OkHttpClient`/`CloseableHttpClient`). Ядро — 0 зависимостей.
   `benchmarks` — на `project(':engine-*')`, прототипы из
   `ru.jrestly.benchmark.engine` удаляются (один источник правды).
2. **Автообнаружение**: ServiceLoader-регистрация `HttpEngineProvider`
   в каждом субмодуле, `isAvailable()` через `Class.forName`.
   `JdkHttpEngine` провайдером **не является** (остаётся fallback'ом) —
   поведение ядра у пользователя без субмодулей не меняется.
3. **Приоритеты**: `default int priority()` в `HttpEngineProvider`
   (бинарно-совместимое расширение), резолвер — стабильная сортировка по
   приоритету, официальным адаптерам 50 (равенство → порядок ServiceLoader,
   документировать явный выбор при обоих на classpath).
4. **Контракт паритета** — чек-лист по полям `HttpEngineOptions`:
   timeout (callTimeout / RequestConfig), streamResponse (byteStream /
   entity content), version (best-effort), прогресс-листнеры с финальным
   событием и нулевой загрузкой, trailers, `close()` с уважением
   `ownsClient`. Исключительный контракт без изменений.
5. **Маппинг ModuleInfo** в `createEngine`: SSL (ADR-0020) → TLS-транспорт,
   CookieHandler → CookieJar/CookieStore (ADR-0032/0039), ProxySelector →
   per-request прокси (ADR-0037), Authenticator → challenge-интерцептор
   best-effort, virtual threads → virtual-thread executor для колбэков.
6. **Адаптер body publisher**: выкачивание JDK `Flow.Publisher<ByteBuffer>`
   → `InputStream` одним адаптером на стриминг (ADR-0035) и multipart
   (ADR-0024) — единственный «чужой» тип в wire-модели, остальное
   платформо-независимое.

Найдено при исследовании (записано в грабли ADR): `sendAsync` OkHttpEngine
закрывает `Response` в колбэке (стриминг в async не читается),
Apache5 `sendAsync` — supplyAsync на общем ForkJoinPool (истощение потоков),
оба прототипа игнорируют timeout/version/stream/progress и не
регистрируются в ServiceLoader.

**Грабли/находки:**
- Приоритет ServiceLoader-провайдеров — явная недетерминизация
  «первый доступный» в `HttpEngineResolver`; решается `priority()` +
  стабильная сортировка.
- `HttpRequest.BodyPublisher` — из `java.base`, а не из чужой зависимости,
  поэтому генерализация wire-типа не обязательна (Non-Goal, отдельный ADR
  при необходимости).

**Гейты:** ядро не менялось — `./gradlew test` зелёный (UP-TO-DATE, 1058/1058),
0 warnings. Изменены: ADR-0058, DRAFT.md, дневник, mailbox, last_session.

### 🛠️ Сессия #155

**Разгадка «проклятия» сессий #150–#154 + фикс дедлока `PublisherInputStream` (фаза 2a ADR-0058 добита до коммита).**

- В дереве нашлись незакоммиченные следы сессий #150–#154: субмодуль `engine-okhttp`

- Причина найдена в старых `test-results`: полный прогон **зависал** на
  `OkHttpEngineParityTest.streamingBodyPublisherIsDrained` (в прошлом прогоне тест
  провисел 488 с и JVM убило лимитом сессии) — так эти сессии и умирали до коммита.
- Диагноз (по jstack зависшего воркера): в `OkHttpEngine.PublisherInputStream`
  маркер `END_OF_STREAM` одноразовый — `read(8192)` добирает остаток последнего
  чанка, попутно съедает END из очереди и возвращает данные; следующий `read`
  поллит уже пустую очередь **вечно**. Второй латентный баг там же: ошибка
  публикатора (`FailureHolder` в очереди) обрабатывалась `continue` без повторной
  проверки `failure` — тоже вечное ожидание.
- Фикс: липкий `volatile boolean eof` (END / ошибка / закрытие → EOF навсегда;
  ошибка — немедленный `throw`), вспомогательный `toIOException`. Стенд-грабли:
  по-чанково репродьюсер НЕ воспроизводит — нужен именно буферный цикл добивки
  (okio `writeAll`), иначе EOF-проба не съедает маркер заранее.
- Гейты: **хэнг устранён** — `:engine-okhttp:test` теперь завершается за 11 с
  (раньше вечно); **17/21 зелёных, 4 падения** — честный WIP, зафиксировано
  ниже. Ядро не менялось (1048 зелёных на #149).

**4 оставшихся падения паритета (разобрать следующей сессией):**
- `Zero-length download fires exactly one (0, 0) event`: событий 0 вместо 1.
- `Download progress ... Content-Length bodies` и `Streaming download progress ...`:
  `total == -1` вместо Content-Length (100000/30000).
- `Multipart bodies are rendered per RFC 7578`: в теле на сервере нет ожидаемой

**Ведущая гипотеза одного корня для трёх прогресс-тестов:** OkHttp включает

при чтении тела на WireMock-стороне; проверять вторым шагом.

**Стенд-грабли (в копилку):** зависший тест прятал 4 падения — вечный poll-цикл
маскировал прогресс; всегда запускать модульные тесты с внешним `timeout`.

### 🛠️ Сессия #156

**ADR-0058, фаза 2a закрыта: `:engine-okhttp` полностью зелёный (23/23).**

- Разобраны 4 падения из WIP #155 — методом зонда (временный `ProbeTest`,
  печать сырых заголовков запроса/ответа и multipart-тела через WireMock).
  Факты оказались важнее гипотез: корней два, не один.
- **Прогресс-тесты (`total == -1`, 0 событий):** OkHttp `BridgeInterceptor`
  при отсутствии `Accept-Encoding` инжектит `Accept-Encoding: gzip` и
  **прозрачно распаковывает** ответ — снимает `Content-Encoding`, теряет
  `Content-Length` (`contentLength() == -1`), тело отдаёт распакованным.
  Это ломало и `total` (ADR-0033), и `isDecompressionEnabled()==false`
  (ADR-0021), и метаданные `Content-Encoding` для ядра.
- **Второй корень прогресс-падений (стенд!):** WireMock 3.12 (Jetty) без
  явного `Content-Length` в стабе ВСЕГДА отвечает `Transfer-Encoding: chunked`
  (проверено curl'ом через wiremock-standalone). Core-тесты прогресса поэтому
  декларируют CL явно — parity-тесты #150–154 этого не делали. Фикс стабов
  зеркалит core (`withHeader("Content-Length", ...)`, для пустого — "0").
- **Multipart-падение — баг теста, не движка:** канонический рендер text-части
  (сверено с core-эталоном `MultipartTest.expectedLegacyBody`) содержит строку
  `Content-Type: text/plain; charset=UTF-8` между `Content-Disposition` и
  пустой строкой. Ассерт ждал её отсутствия.
- **Фикс движка — пассивный транспорт (два интерцептора):**
  `NoTransparentGzipInterceptor` (application: при отсутствии `Accept-Encoding`
  подставляет `gzip` + tag-маркер, чтобы Bridge не включил прозрачность) и
  `StripSuppressedAcceptEncodingInterceptor` (network: снимает подставленный
  заголовок ровно перед проводом). Итог: на проводе заголовка нет — точный
  паритет с `JdkHttpEngine`; явный `Accept-Encoding` вызывающего проходит как
  есть, ответ приходит сжатым с живым `Content-Encoding`. Оборачивается и
  внешний `OkHttpClient` (движок = контракт, не сырой OkHttp).
- **TDD:** red-first подтверждён — `noAcceptEncodingInjectedByTransport`
  красный до фикса (`containsHeader("Accept-Encoding") == true`), зелёный после;
  `explicitAcceptEncodingIsPassedThroughCompressed` — регрессионный
  предохранитель (зелёный до и после).
- ADR-0058 дополнен секцией Amendment (решение + побочная находка WireMock).
- **Бонус-находка:** javadoc-гейт субмодуля (`-Xdoclint:all -Werror`, как у ядра)
  в WIP #150–154 **никогда не был зелёным**: `{@link JdkHttpEngine}` не
  резолвился (класс ядра не заимпортирован — javadoc не видит simple name без
  импорта) + implicit default concrete constructor у `OkHttpEngineProvider`
  (doclint missing: «use of default constructor, which does not provide a
  comment»). Фикс: импорт `JdkHttpEngine` и явный конструктор с javadoc.
  `:engine-okhttp:javadoc` теперь зелёный.

  уходит **под чужим заголовком**:

  Причина ясна по коду: `requestType` (ветка сериализации, `:289`) и
  `@ContentType` (только заголовок) разведены, а `createJsonBodyPayload` всегда
  зовёт `getJsonCodec()` (`:811`).
- Ответный путь тоже слеп к `Content-Type` ответа — все 5 call-site'ов

  (`resolveOrDefault` → JSON-by-default ради строгой обратной совместимости)
  + `JsonCodecAdapter` (мост, claim'ит `application/json`/`*+json`, чтобы
  нетронутый `JsonCodec` жил дальше). Селекция по request `Content-Type`
  (явный заголовок → `@ContentType` → `requestType.mime()`) и по response
  `Content-Type` (charset через ADR-0056); fail-fast вместо тихой подмены на
  запросе. Raw-типы по-прежнему минуют кодек.
- **Non-goals:** парсер XML/XSD в ядре (ADR-0003), полный content-negotiation
  (q-value), изменение raw/SSE-путей, ломка `JsonCodec`/`jsonCodec(...)`.
- **Фазы:** Ф1 — SPI ядра (селекция + кэш кодека в `HttpTemplate`, иначе
  регрессия zero-garbage ADR-0055); Ф2 — субмодуль `jrestly-codec-jackson-xml`
  (zero-dep ядро); Ф3 — ServiceLoader-автоподбор (по прецеденту движков ADR-0058).
- **Гейт:** код не менялся (только ADR + память); полный
  `./gradlew test javadoc` зелёный, **1153/1153** (состояние #176 сохранено),

- **Мысль:** такие «невидимые» пробелы живут на стыке двух честных по
  отдельности подсистем (`@ContentType` врёт именно потому, что заголовки умеют
  произвольный тип, а кодек — нет). ADR доводит обе половины до общего media-типа.

### 🛠️ Сессия #183

**Аудит (4-й шаг нити «общие мутабельные структуры»): `AuthHeaderProvider` —
рассинхрон `isAuthorized()` с реально отправляемым и неатомарная пара кредов.**

- **Что искал.** Продолжение #181/#182: прошёл фонарём по `AuthHeaderProvider`
  (единственный оставшийся общий мутабельный холдер клиента; в #182 помечен как
  «минорная видимость»). Оказалось — не минорно: там два независимых дефекта.
- **Находка 1 (детерминированная, логическая).** `isAuthorized()` возвращал
  `initialHeaderName != null || headerValue != null`, тогда как
  `getAuthHeaders()` отправляет креды только при **обеих** непустых частях.
  Значит имя-без-значения (или `updateAuthHeader(null, v)`) → `isAuthorized()`
  = true, `isLoginInBackgroundNeeded` не дёргает логин, а на провод уходит
  **пусто**. Тихая «авторизация в никуда»: клиент считает себя авторизованным,
  запросы неавторизованы. Это ровно противоречит javadoc `Builder.authHeader`
  («sent only when both name and value are set; a client started without it is
  not authorized until login captures a credential»).
- **Находка 2 (потоковая).** Пара `headerName`/`headerValue` — два **не-volatile**
  поля, пишутся из `@SetAuthDetails`-капчура/`updateAuthHeader` неатомарно:
  читатель в `getAuthHeaders()` может увидеть **рваную** пару (имя одного
  обновления + значение другого) — та же болезнь общего мутабельного state,
  что в #181. Стресс-тест поймал рваную пару на старом коде.
- **Fix.** Один неизменяемый `Header`, опубликованный через `volatile`:
  `private final Header initialHeader` + `private volatile Header capturedHeader`,
  фабрика `complete(name, value)` (пара или null — неполная не хранится).
  `getAuthHeaders()` и `isAuthorized()` читают один и тот же снимок →
  инвариант «authorized ⇔ есть что отправить». Побочно: `getAuthHeaders()`
  больше не аллоцирует `new Header` на каждый вызов (переиспользует
  закэшированную пару) — в духе zero-garbage ADR-0055.
- **TDD red-first.** Новый `AuthHeaderProviderTest` (6 тестов): неполная
  пара не авторизует/не шлётся; полная — авторизует/шлётся; полное обновление
  важнее initial и очищается в initial; инвариант по всей матрице состояний;
  стресс «два писателя + два читателя» не должен увидеть рваную пару.
  На старом коде — **4 красных** ровно ожидаемо (включая стресс), после фикса
  зелёные.
- **Грабли/мысль.** Все ловятся одним фонарём: холдер честен в «счастливом
  сценарии» (обе части всегда приходят вместе при капчуре), а расходится на
  неполном/конкурентном вводе. `isAuthorized()` — «производная» от состояния,
  и стоило ей вывести себя из того же снимка, что и `getAuthHeaders()`.
- **Гейты.** `./gradlew test javadoc` — **1196/1196** (core 1116 +
  engine-okhttp 25 + engine-apache5 25 + codec-jackson-xml 15 + benchmarks 15),
  javadoc корня и субмодулей зелёный под `-Werror`, 0 warnings. Эпики/ADR не
  трогались.

**Аудит (5-й шаг нити «тихие рассинхроны контракта»): `RetryPolicy` — дефолтный

- **Что искал.** После закрытия общих мутабельных холдеров клиента (#181–#183)

  `RetryPolicy` (сложная чистая математика, читается как эталон).
- **Находка.** Принятое решение ADR-0040 говорит буквально:
  `maxRetryAfter(Duration)` «дефолт: null, **при обращении fallback на
  maxBackoff**» и `@Retry.maxRetryAfterMs() default -1` («-1 означает дефолт
  `maxBackoffMs`»), а пункт 3 «Защита от зависаний по `Retry-After`» ради этого
  и заведён. Код же применял потолок **только** при явно заданном значении:
  `if (maxRetryAfter != null) { … }` — при дефолте `Retry-After` уходил
  **неограниченным**. `Retry-After: 86400` → поток спит **24 часа** (то самое
  зависание, против которого ADR). Расхождение — только в коде: и builder-javadoc
  («If null, maxBackoff is used as the cap»), и формула в class-javadoc уже
  описывали fallback; «no cap applied» в `getMaxRetryAfter()` — производная
  формулировка, подогнанная под баг.

  wall-clock теста `RetryTest` (`retryAfterHeaderRaisesTheWaitDeterministically`,
  `retryAfterHttpDateRaisesTheWaitDeterministically`) держали именно
  недокументированное «без потолка» — `maxBackoff` 50 мс, а `Retry-After` 1 с/3 с
  и ожидание `>= 1000`/`>= 2000` мс. Эти тесты и были «зелёной маской» бага.
- **Fix.** Эффективный потолок: `maxRetryAfter != null ? maxRetryAfter.toMillis()

  Javadoc геттера и классовая формула уточнены (`cap` вместо `maxRetryAfter`).

- **Два старых теста — приведены в соответствие.** `RetryTest` теперь явно

  что по-прежнему проверяют «заголовок поднимает ожидание», но больше не
  опираются на отсутствие потолка. ADR-0040 дополнен `## Amendment #184`
  (решение ADR не менялось — код приведён к нему).
- **Грабли/мысль.** Это первый случай в серии, когда расхождение не между
  подсистемами, а между **принятым ADR и его реализацией**, причём документация

### 🛠️ Сессия #187

**Аудит-нить возобновлена: `SingleFlightTokenManager` — завершившийся лидер затирал
свежий in-flight future.**

- **Старт: WIP прерванной сессии.** В дереве — незакоммиченные изменения #186
  (память не успела): фикс `SingleFlightTokenManager` (2 строки) + новый
  детерминированный тест в `TokenManagerTest`. Счётчик уже был 187. Принял WIP как
  свой (паттерн #175): проверил, допроверил red-first, зафиксировал.
- **Подозрение (из last_session #185).** `invalidate()` безусловно чистит
  `inFlight` (`set(null)`); завершающий лидер тоже делал `inFlight.set(null)` и
  мог сбросить **новый** future, который другой вызывающий установил после
  `invalidate()`. Single-flight ломается: следующий вызывающий не присоединяется к
  висящей аквизиции, а стартует новый supplier-вызов — thundering herd на
  auth-сервер, ровно то, что class-javadoc обещает предотвратить.
- **Fix.** Лидер чистит только свой future: `inFlight.compareAndSet(future, null)`
  в success- и failure-ветках. Если `invalidate()` его осиротила, CAS не проходит
  (в `inFlight` — свежий future или null) — свежий future остаётся и продолжает
  делиться.
- **TDD red-first (подтверждено на старом коде).** `git stash` main-фикса → новый
  тест `finishingLeaderDoesNotClobberNewerInFlightAcquisition` красный ровно по
  single-flight-ассерту (третий supplier-вызов начался в 300 мс), после фикса —
  зелёный. Тест детерминирован: 3 пул-нити, 4 latch'а, без blind-wait'ов; финал —
  `invocations == 2` и оба поздних вызывающих получают "tok-2".
- **Гейты.** `./gradlew test javadoc` — **1198/1198** (core 1118 + engine-okhttp
