[2026-10-19 23:20] Агент (сессия #313): Антон, пообещал — сделал: **ADR-0068 готов** (`docs/0.11.0/ADR-0068-real-feed-benchmark-fetch-and-parse.md`, Proposed). Суть:
- *Сценарий (настоящий):* fetch ленты (RSS 2.0 / Atom 1.0, по 20/200/1000 записей с реальной сложностью лент — CDATA, entities, namespaces, RFC 822 даты; фикстуры детерминированные, живой интернет из JMH исключён ради репродуцируемости) → **общий StAX-парсер** (один код для всех клиентов — сравнивается вклад HTTP-библиотеки, а не XML-биндингов) → fold в агрегат.
- *Парсер НЕ в ядре* — по твоему слову: без SPI, без субмодуля, без `PayloadCodec`-расширений; всё в не-публикуемых `benchmarks/` (ADR-0049).
- *Главный разрез:* buffered (`@Get byte[]`) vs streaming (`@Get InputStream` прямо в парсер, без полной копии тела) — гипотеза: streaming заметно снижает alloc/op на больших лентах.
- *Метрики (все три твоих):* ops/sec (JMH Throughput — основной), mem (`-prof gc`, B/op), CPU (in-harness `getProcessCpuTime()`-проба + cross-check `/usr/bin/time -v`).
- *Стенд:* расширение `BenchmarkHttpServer` лент-маршрутами с пре-вычисленными телами + латентностный гейт в стиле `BenchmarkHttpServerTest`.
- *Фазы:* Ф1 фикстуры+стенд → Ф2 парсер+клиенты → Ф3 JMH+публикация в BENCHMARKS.md. Матрица конкурентов — та же, что в текущей большой таблице.
