## 1. Проблема

Сверка объёма деклараций контроллеров jRestly против эталонных конкурентов
(Retrofit 2.11, OpenFeign 13.5, Spring 6 HTTP Interfaces) показывает **три реальные
точки многословности** — все локализованы в декларациях контроллеров, билдер
сопоставим по всем четырём библиотекам (`baseUrl` + конфигурация).

Эталонная декларация «get one item» у конкурентов:

```java
// Retrofit 2.11
@GET("users/{id}")
Call<User> getUser(@Path("id") String id);

// OpenFeign 13.5 (classic)
@RequestLine("GET /users/{id}")
User getUser(@Param("id") String id);

// Spring 6 HTTP Interfaces
@GetExchange("/users/{id}")
User getUser(@PathVariable String id);
```

jRestly сегодня:

```java
@Get(path = "/users/${id}")
User getUser(@PathVariable(name = "id") String id);
```

Разрыв не в механизме (прозрачные типы возврата — наш выигрыш, ADR-0004), а в
объёме **обязательного текста на строку**:

| # | Точка многословности | У нас | У конкурентов |
|---|----------------------|-------|---------------|
| V1 | Атрибут пути глагола | именованный `path = "…"` | неявный `value` (`@GET("…")`, `@RequestLine`, `@GetExchange`) |
| V2 | Имя в параметрных биндингах | `@PathVariable(name = "id")` в декоративной манере README/примеров (fallback на имя Java-параметра уже работает: `name().isEmpty() ? java param`, ADR-0017) | Spring/Feign — неименованные/короткие; Retrofit требует `@Path("id")`, но Spring-стиль неименованный |
| V3 | Синтаксис плейсхолдера | `${id}` | `{id}` — единый отраслевой стандарт (Retrofit/Feign/Spring/URI-шаблоны RFC 6570) |

Плюс периферийные (наблюдения, не основные):

- `requestType = RequestType.APPLICATION_FORM_URLENCODED` — длинная квалификация
  для form/multipart (у Retrofit — маркер `@FormUrlEncoded`);
- `@Get(params = {@RequestDefaultParam(name = "size", value = "10")})` — вложенная
  аннотация-массив для статических query-дефолтов; гипотетически, если
  `@Get("/items?size=10")` уже работает (путь проходит через `URI.create`-валидацию
  ADR-0025 §легальность — `?` легален), то этот текст избыточен — **требует проверки**.

## 2. Решение: пакет предложений (по убыванию соотношения эффект/цена)

Все предложения не ломают инварианты: zero-dep, прозрачные методы, анти-комбайн,
fail-fast валидация. Обратная совместимость не требуется (слово Антона).

### P1 — `value` как основной атрибут глаголов (рекомендую: да)

`path()` глаголов (`@Get/@Post/@Put/@Patch/@Delete`) → **`value()`** (атрибут по
умолчанию). Эффект: `@Get("/users/${id}")` вместо `@Get(path = "/users/${id}")`
— самый повторяемый токен контроллера, минус 7 символов × на каждый метод.
Механика: rename атрибута в 5 файлах аннотаций + все call-site'ы
(`MethodMetadata`, валидатор, тесты, fixtures, README). Механическое замещение,
риск ≈ нулевой — компилятор поведёт за руку, поведение запросов не меняется. Альтернатива (отвергнута): держать
оба атрибута и ругаться при одновременном использовании — ниша «два способа
сказать одно» против чистоты.

### P2 — безымянные биндинги в примерах и fixtures (рекомендую: да, бесплатно)

Код не меняется вовсе: `@PathVariable(name = "id") Long id` → `@PathVariable Long id`,
`@RequestParam(name = "page") Integer page` → `@RequestParam Integer page` —
fallback уже реализован (ADR-0017) и защищён fail-fast'ом #212 (без флага
`-parameters` пустое имя при недоступном JVM-имени ловится сразу, при создании прокси).
Эффект — только в README/fixtures/javadoc-примерах: страницы документации
перестают учить многословию там, где оно не нужно. Явный `name` остаётся
однозначным способом разрулить `@RequestParam("q") String query` при имени
параметра-дискриминатора (query ≠ q).

### P3 — плейсхолдер `{id}` вместо `${id}` (запрос решения Антона)

Единый отраслевой стандарт (`{name}`); смена трогает мышечную память. Цена: не
пустячная, хотя механическая — `validatePath` (маска `${...}` → маска `{...}`,
та же same-length замена), экстрактор плейсхолдеров валидатора (#210),
`createUrl`/`createUri` replace, весь массив `${}` в тестах/README/javadoc.
Коллизий не предвидится: `{`/`}` по RFC 3986 в URI нелегальны вовсе,
поэтому `URI.create`-гейт (#211) отлавливает «случайные» `{}` в пути, а
same-length-маска плейсхолдеров (та же, что у `${...}`) прогоняет легальные шаблоны. Вопрос Антону: менять или
оставить фирменный `${}`? Оба варианта валидны; `{}` берёт знакомостью
и паритетом с конкурентами, `${}` — самобытностью (визуально громче, но
в аннотации-константе интерполяции всё равно не бывает).

### P4 — проверить и задокументировать статические query прямо в пути (самый дешёвый, нужна микропроверка)

Если `@Get("/api/items?size=10")` (+ merge с динамическими `@RequestParam` и
с path-плейсхолдерами) уже корректно работает — документировать как
рабочий способ статического дефолта и отодвинуть `@RequestDefaultParam` в
нишу (многозначные дефолты, значения со спецсимволами, явная форма). Если
merge кривой — это баг, чинить по TDD в отдельной сессии. Проверка
маленькая, ценность документационно серьёзная.

### P5 — form/multipart RequestType (рекомендую: не трогать сейчас)

`requestType = RequestType.APPLICATION_FORM_URLENCODED` остаётся. Вариант «маркер
`@FormUrlEncoded`/`@Multipart`» вводит второй механизм декларации одного и того
же + открытие семейного ряда: в Retrofit маркер `@FormUrlEncoded` тянет за
собой `@Field`/`@FieldMap`, а эти роли у нас давно играют `@RequestParam`/`@RequestParam(Map)`.
Анти-комбайн и «один механизм на одно» перевешивают 30+ символов на редкие
методы. Возврат к теме — если Антон сочтёт иначе.

## 3. Non-goals

- Не переизобретаем `@RequestLine` Feign (строку «GET /path» статически
  проверять заметно сложнее, чем enum-глаголы + fail-fast валидатор).
- Не добавляем Response-оболочки (ADR-0004 навсегда).
- Не трогаем билдер (`baseUrl`, auth, codecs, resilience — уже компактнее конкурентов
  за счёт SPI-композиции, а не мешка централизованных флагов).

## 4. Verification

Исследовательский ADR: код не менялся. Гейт не запускался — последний зелёный
1,636/1,636 (сессия #283) в силе. P1 расценивается как механический rename без
поведенческого эффекта; для P3/P4 последуют TDD-сессии после решения Антона.

## 5. Pattern

- Меры лаконичности = «не нёсущий смысл текст» (V1 `path = ` — нулевая ценность)
  ≠ «частые, но семантически нагруженные» (явный `name`) — различать при рефакторинге API.
- Проверять каждую «зачем так?» гипотезу по коду: fallback безымянных биндингов
  уже был реализован — реальный пробел оказался не в коде, а в примерах,
  учащих многословной форме.

## Amendment #293 (2026-10-19): P2 реализован

*P2 исполнен как чистый документационный прогон* (поведение запросов не
меняется — fallback на имя Java-параметра реализован ADR-0017 и защищён
fail-fast'ом #212): 32 файла, 93 строки — README (8), javadoc
`DownloadProgressListener` (1), shared fixtures `TestController`/
`PathVariableController`, benchmarks (2) и поведенческие тесты (WireMock/
integration). Правило, применённое программно: `@Ann(name = "X") T x` →
`@Ann T x` **тогда и только тогда**, когда `X == x` и в скобках нет второго
атрибута. Явный `name = ` сохранён ровно в своей нише: `query ≠ q`,
`tag ≠ tags`, `Accept ≠ acceptOverride` (дискриминаторы), второй атрибут
(`encoded = true`, `format = …`, `contentType = …`) и статические
декларации (`@RequestHeader(name = …, value = …)`, `@RequestDefaultParam`,
`@MultipartFormFile(partName = …)`). Тесты декларативной семантики
(`ControllerValidationTest`, `MethodMetadataTest`, `*ValidationTest`,
`HttpTemplateBuilderTest`) осознанно не тронуты — там атрибут `name` есть
объект наблюдения, а не декор.

*Факты, проверенные кодом для прогона:*

- Bare-форма `@PathVariable T x` компилируется у всех четырёх аннотаций
  параметрических биндингов, потому что `name()` имеет `default ""` —
  грабля #292 (implicit `value` — только один абстрактный метод) бьёт по
  синтаксису `@Ann("…")`, а не по пустым скобкам.
- Исключение — `@MultipartFormFile.partName()`: default'а нет, поэтому
  `partName = ` держится всегда, даже при совпадении с именем параметра.
- `-parameters` стоит и в `compileJava`, и в `compileTestJava` (build.gradle
  всех 5 модулей) — fallback в тестах/фикстурах надёжен.
- Spring-бенчмарк (`SpringRestClientBenchmarkClient`) не тронут: его
  `@PathVariable("id")` — аннотация Spring с единственным `value()`.

*Находка прогона — fallback на имя параметра неполон для Map-префикса:*
первый гейт упал на двух тестах `GetMethodTest` (prefixing `name[key]`) —
`HttpTemplateBuilder` строит префикс из `rawRequestParamName()`, а не из
эффективного имени (с fallback'ом ADR-0017): bare `@RequestParam Map filter`
раскрывается в голые `status=…`, а `@RequestParam(name = "filter") Map filter`
— в `filter[status]=…`. Это **задокументированное** поведение README
(префикс — «if `@RequestParam.name()` is specified»), так что в рамках
«кода не меняется» декларация `GetMethodTest.searchWithPrefixedMap`
вернулась к явной форме (атрибут там — объект наблюдения, как в
`*ValidationTest`). Хвост в беклог: либо довести fallback до Map-префикса
(bare и named станут полностью эквивалентны), либо задокументировать
различие явно — решать в отдельной сессии.

Гейт **1,637/1,637** green across all 5 modules (число тестов не изменилось
— правки декларативные), javadoc чист под `-Werror`. Исторические снапшоты
(`docs/0.9.0/`, `docs/0.10.0/`, `ROADMAP.md`, §1 «jRestly сегодня» этого
ADR) не переписаны — осознанно. Дальше: **P3** (`${id}` → `{id}`).
